Tideborne/Compatibility
Requirements & migration

Clean internals without abandoning old worlds.

Tideborne's P1–P10 cleanup removed historical internal ownership while deliberately preserving public IDs, save keys, network identities and migration paths that existing worlds can depend on.

Tide

Tide is the required fishing foundation. Tideborne extends its fishing experience rather than redistributing or replacing Tide-owned systems.

Optional integrations

Apex Waters and Myths of the Sea have optional compatibility paths in the current project. Optional-mod code is isolated so the absence of those mods does not force their classes to load on a normal Tideborne install.

Historical Tideborne identities

Old namespaces and IDs can remain in persistence or compatibility boundaries even though they no longer own active architecture. That distinction is intentional: removing an old Java package is safe; casually renaming a persisted item or payload ID may not be.

Player takeawayYou should not need to understand names like historical internal sub-mods during normal play. They appear only in advanced/reference documentation when they matter for migration or diagnostics.

Old worlds

Tideborne keeps explicit migration and legacy-ID ownership so older specimen/config/resource identities can be interpreted without letting historical models become the canonical current Fishing System again.
